**Date:** 2026-09-19 · **Commit:** `3b22351` · **Scope:** entire `src/`, all 9 Edge Functions, `db_dump.sql`, all 14 migrations, build/deploy config

**Baseline:** `npx tsc --noEmit` → 0 errors. `npm run build` → succeeds, 23 routes. Both are misleading: `src/lib/supabase.ts` types the client as `any`, and `tsconfig.json:37` excludes `supabase/` from type-checking. Every critical below passed a "clean" build.

## Part 1 — Critical defects

### C-01 · Infinite render + network loop on every open session
`src/components/layout/AppShell.tsx:46-51` · `src/store/purchases.ts:29` · `src/store/auth.ts:137`

`useEffect(..., [user])` → `checkVipStatus()` → `fetchProfile()` → `set({ user: userProfile })` where `userProfile` is a **fresh object literal every call**. Zustand v5 compares with `Object.is`, so the dep changes forever. Only exit is `supabase.auth.getUser()` returning no user.

**Symptom:** while any logged-in user keeps a tab open, `/auth/v1/user` + `users?id=` + `subscriptions?` fire several times per second indefinitely. Mobile battery/data drain, Supabase GoTrue + PostgREST 429s that break sign-in for everyone behind the same NAT/CGNAT IP, runaway API billing.

**Fix:** dep → `[user?.id]`, and remove the `fetchProfile()` call from `checkVipStatus` (its other caller, `upgrade/page.tsx:47-49`, already calls it separately). Belt-and-braces: skip `set` in `fetchProfile` when shallow-equal.

### C-02 · `refund_ai_credit()` grants infinite AI credits to any logged-in user
`db_dump.sql:431,440-441` · `supabase/migrations/009_security_hardening.sql:116-126`

`security definer` + `grant execute ... to authenticated`, body is an uncapped `update users set ai_credits = ai_credits + 1 where id = auth.uid()` with no proof a credit was consumed. `security definer` bypasses the column-level grant at `db_dump.sql:343`. Contrast `increment_ai_credits`, correctly revoked from both `public` and `authenticated` at `:710-711`.

**Symptom:** `for (let i=0;i<1000;i++) supabase.rpc('refund_ai_credit')` in the browser console → unlimited credits. Defeats the free tier and the whole referral reward economy. Silent.

**Fix:** `revoke all on function refund_ai_credit() from authenticated;` — **and** switch its two call sites (`monthly-conclusion/index.ts:69,76`) to a service-role client, mirroring how `midtrans-webhook` calls `increment_ai_credits`. Audit `consume_ai_credit` and `check_rate_limit` the same way (both are also `security definer` + `authenticated`).

**Status — fixed in working tree, not yet deployed (2026-09-19).** Correction to this finding: the call sites are **16, not 2** — `chat-financial` (5), `parse-receipt` (6), `monthly-conclusion` (5), across all three AI functions. No client code calls it.
- `supabase/migrations/015_lock_down_ai_credit_refund.sql` — adds `refund_ai_credit_for(p_user_id uuid)` (`security definer`, `set search_path`, revoked from `public`/`anon`/`authenticated`, granted only to `service_role`) and **drops** `refund_ai_credit()` outright.
- All 16 refund call sites moved to a module-level service-role `adminClient`, mirroring `midtrans-webhook`.
- `db_dump.sql` synced so re-applying the dump cannot reopen the hole. Migration `009` left untouched (historical record; `015` supersedes it).
- Companion audit, as instructed: **`consume_ai_credit()` is safe to leave granted to `authenticated`** — its `where id = auth.uid()` is forced to the caller and `ai_credits > 0` blocks negatives, so the worst self-inflicted outcome is burning your own credits. **`check_rate_limit(text,int,int)` likewise** — `user_id` is `auth.uid()`, so a caller can only inflate their own buckets (no cross-user lockout, no way to skip a limit an Edge Function enforces with its own `p_action`/`p_max`). Its one real weakness is unbounded row growth from arbitrary `p_action` strings; that is a Part 4 storage concern, not a privilege hole.
- **Deployed (live environment — 2026-09-19):** `015_lock_down_ai_credit_refund.sql` applied via `supabase db push`. Edge functions `chat-financial`, `monthly-conclusion`, and `parse-receipt` successfully deployed (`--no-verify-jwt`).
- **Runtime dependency:** all three functions rely on `SUPABASE_SERVICE_ROLE_KEY` (verified present in project secrets) to call `refund_ai_credit_for`.

### C-03 · December always returns zero transactions
`src/store/transactions.ts:73-75`

```ts
const endDate = `${year}-${nextMonth === 12 ? '01' : String(nextMonth + 1).padStart(2, '0')}-01`;
```

For `month = '2026-12'` → `endDate = '2026-01-01'`. **The year is never incremented.** Query becomes `.gte('transaction_date','2026-12-01').lt('transaction_date','2026-01-01')` — an empty range.

**Symptom:** throughout December, Home / Transactions / Stats / Budget / Export all show Rp 0 income, Rp 0 expense, "Belum ada transaksi di bulan ini", 0% budget, streak → 0, export refuses. Users believe they lost all their data. `MonthPicker.tsx:22-26` has no future clamp, so anyone can tap into December **today** and see the same emptiness.

**Fix:** `date-fns` is already a dependency — `const endDate = format(addMonths(parseISO(`${month}-01`), 1), 'yyyy-MM-dd')`. Delete the hand-rolled arithmetic. Also clamp `MonthPicker` to `getCurrentMonth()`.

### C-04 · Wallet balance is non-atomic browser math, committed even when the insert failed
`src/store/transactions.ts:113-136` (add), `160-201` (update), `212-247` (delete)

Four compounding defects:
1. **No DB trigger exists.** The only trigger in the entire schema is `on_auth_user_created`. No `pg_cron`, no Edge Function touches `transactions` or `wallets.balance`. Balance is `SET balance = <absolute value computed in the browser>`, not `balance = balance + delta` → two tabs/devices = lost update.
2. **The `.update({ balance })` at `:130-136` has no `if (!error)` guard** — a rejected insert (FK, RLS, network) still permanently mutates the stored balance.
3. The base value can be the `localStorage` cache or the invented `DEFAULT_WALLETS` (see C-13).
4. **No reconciliation path.** `wallets/page.tsx:88` deliberately excludes `balance` from the edit payload, and `:235` hides the balance input when editing.

**Symptom:** the "Total Akumulasi" figure on Home and `totalBalance` on the wallets page silently disagree with the sum of the transaction list, and the gap grows monotonically. **Once it drifts the user can never correct it.** This is the headline number of a finance app.

**Fix:** add a `SECURITY DEFINER` RPC `apply_balance_delta(p_wallet_id, p_delta)` or a DB trigger so balance is derived inside the same transaction as the write; delete all three client-side `.update({ balance })` blocks. **Do C-14's RLS ownership check first** — otherwise the trigger becomes a cross-tenant hole. Interim: make balance editable and add a "recompute from transactions" action.

### C-05 · Failed inserts still render as saved, and are cached forever
`src/store/transactions.ts:138-152`

```ts
let savedTx = newTx;
if (!error && data) { savedTx = data as Transaction; }
const transactions = [savedTx, ...get().transactions];   // runs even when error is truthy
set({ transactions });
localStorage.setItem(`finy_txs_${userId}`, JSON.stringify(transactions));
```

On error the locally-fabricated `newTx` (with a `crypto.randomUUID()` id that exists nowhere in Postgres) is prepended **and persisted**.

**Symptom:** user records Rp 250.000, sees a red "Gagal mencatat transaksi" toast, *and* sees the transaction in the list with the balance updated. Vanishes on reload — or reappears from the poisoned cache when offline. Money silently never recorded.

**Fix:** `if (error) return { error, data: null };` before touching `transactions`/`localStorage`; only prepend on success; roll back the optimistic wallet delta.

**Status — fixed in working tree (2026-09-19), `npx tsc --noEmit` clean.** `addTransaction` now captures `prevWallets`, and on `error || !data` it does `set({ wallets: prevWallets })` and returns `{ error, data: null }` **before** any write to `transactions` or `localStorage`. The fabricated `crypto.randomUUID()` row is gone — only the server-returned `data` is prepended and cached, and the wallet-balance `.update()` now runs strictly after the row exists. (The separate non-atomic balance math in `updateTransaction`/`deleteTransaction` is C-04's scope, not touched here.)

### C-06 · Enabling the PIN lock permanently locks the user out of their own app
`src/store/security.ts:23-34` · `src/app/(app)/security/page.tsx:31-33` · `src/components/layout/AppShell.tsx:73-75`

`initialize()` sets `isLocked: isEnabled` **unconditionally**, and `/security` calls `initialize()` in its own mount effect. `AppShell` returns `<AppLock />` in place of the whole tree whenever `isLocked`, unmounting the security page.

**Symptom:** enable PIN → visit Security → `initialize()` locks → AppLock replaces the page → correct PIN → `isLocked: false` → page remounts → `initialize()` locks again. **Hard infinite loop.** The only page containing the "disable PIN" toggle is the page you cannot reach. Escape requires manually clearing localStorage.

**Fix:** split into a one-time `hydrate()` (reads `pin`/`isEnabled` only) and an explicit `lock()`; only AppShell's cold-start path may set `isLocked: true`. Remove the `initialize()` call from `security/page.tsx:31-33`.

**Status — fixed in working tree (2026-09-19), `npx tsc --noEmit` clean.** Implemented the equivalent guard rather than a literal hydrate/lock split: `initialize()` now early-returns on `get().initialized`, so it may set `isLocked: isEnabled` **only on cold start**, and the mount-time `initialize()` was deleted from `security/page.tsx` (replaced by a comment). `AppShell` is the sole `initSec()` caller and gates rendering behind `secInitialized`. `setPin()` explicitly sets `isLocked: false`, so enabling PIN from the page no longer locks the tree. The remount→re-lock→remount loop is broken. Note: `lock()` still has zero call sites (that is D-12, out of scope here).

**Verified (2026-09-23).** Static trace confirms no code path re-engages the lock after unlock: `initialize()` is called only from `AppShell`'s mount effect (deps are stable Zustand action refs, and the `initialized` flag makes even a hypothetical re-fire a no-op); `AppLock.tsx` uses only `verifyPin`; the security page imports no `initialize`. `npm run build` → exit 0, all 24 routes prerendered incl. `/security`. **Already shipped:** these changes are in commit `82c5cce` which is on `origin/master` (`0/0` ahead/behind), so the web host builds them from master — C-06 is deployed, not merely code-complete. **Final manual QA (user-only):** on the deployed/HTTPS build, enable PIN → open Security → enter correct PIN → confirm no lock loop and the disable toggle is reachable; then cold-reload and confirm it still locks. No migration/Edge Function is involved.

### C-07 · VIP never expires
`src/hooks/useFeatureAccess.ts:8` · `src/store/purchases.ts:39-41` · `verify-payment/index.ts:116-121` · `midtrans-webhook/index.ts:127-131`

Every grant path sets `is_vip = true` + `vip_until`; nothing anywhere sets it back. Grep across the whole repo for `is_vip = false`, `expire_vip`, `pg_cron`, `cron.schedule` → **zero matches**. `useFeatureAccess.ts:8` is `storeIsVip || !!user?.is_vip` — `vip_until` is never compared to `now()`. `purchases.ts:39-41` short-circuits on `user.is_vip` *before* reaching the one place that does check expiry (`:55-60`).

**Symptom:** one Rp 14.999 payment — or one redeemed referral voucher — grants Finy Pro **permanently**. Monthly and annual subscribers are indistinguishable after day 30. The plan card's "Bayar per bulan, batalkan kapan saja" is misleading: there is no subscription to cancel and no renewal to charge.

**Fix:** a `pg_cron` job running `update users set is_vip = false where is_vip and vip_until is not null and vip_until < now();`. Also harden the client: `const isVip = !!user?.is_vip && (!user.vip_until || new Date(user.vip_until) > new Date())`. **Server-side expiry is the one that matters** (see C-16).

### C-08 · `create-subscription` returns a live Snap token even when the DB INSERT fails
`supabase/functions/create-subscription/index.ts:148-172`

The Snap call happens at `:116-129`, the `subscriptions` INSERT at `:148`. On `insertError` the code logs and proceeds, with the comment *"Still proceed with returning token, as orderId is valid and webhook can reconcile"*. **That comment is false** — `midtrans-webhook:82-90` returns `200 {status:'ignored'}` for an unknown `order_id`, and `verify-payment:46-54` returns `404`. There is no third path.

**Symptom:** Midtrans captures the money, Snap fires `onSuccess`, the page toasts "Selamat! Finy Pro aktif" (see H-06), the user is routed home and is still Free. Permanently, with no order record and no audit trail to refund from. **The worst failure mode in the payment flow.**

**Fix:** insert the `pending` row **before** calling Midtrans; mark it `failed` if Snap errors. At minimum `if (insertError) return jsonError('Gagal mencatat transaksi. Jangan lanjutkan pembayaran.', 500);` and do not return the token.

### C-09 · The service worker can never install → the PWA is not installable
`public/sw.js:2-15` · `public/manifest.json:6-21` · `public/` (verified: contains **only** `manifest.json` and `sw.js`)

Two independent, each-fatal problems:
1. `ASSETS_TO_CACHE` includes `/favicon.ico`, which **does not exist** (no `src/app/favicon.ico` or `icon.png` either). `cache.addAll()` is **atomic** — one 404 rejects the whole promise, so `install` fails, the worker never reaches `activate`, and `skipWaiting()`/`clients.claim()` never run.
2. All three manifest icons point at `/favicon.ico`. Chrome requires a PNG ≥192px and ≥512px; `image/x-icon` declared as `"192x192"`/`"512x512"` is never accepted.

**Symptom:** no install banner ever appears on Chrome/Android, `beforeinstallprompt` never fires (so `PWAInstallPrompt`'s non-iOS branch is dead code), no offline support, and iOS "Add to Home Screen" produces a bookmark with a blank/globe icon. Console shows an install error that's easy to miss.

**Fix:** add real `icon-192.png`, `icon-512.png`, `apple-touch-icon.png`; reference them with `"type": "image/png"` and separate `purpose: "any"` / `"maskable"` entries; drop `/favicon.ico` from `ASSETS_TO_CACHE` or switch to `Promise.allSettled` + individual `cache.add`. Bump `CACHE_NAME` per deploy.

**Status — fixed in working tree (2026-09-23).** The four PNGs already existed in `public/` but were unreferenced. `manifest.json` icons rewritten to `/icon-192.png` (any), `/icon-512.png` (any), `/icon-maskable-512.png` (maskable), all `image/png`; the three `/favicon.ico` entries are gone. `public/sw.js`: `ASSETS_TO_CACHE` drops `/favicon.ico`, `cache.addAll()` replaced with `Promise.allSettled(assets.map(a => cache.add(a)))` so one 404 can no longer veto activation, and `CACHE_NAME` bumped to `finy-web-cache-v2`. `layout.tsx` now emits `<link rel="apple-touch-icon" href="/apple-touch-icon.png">` via `metadata.icons.apple`. Verified: `node --check public/sw.js` passes, `manifest.json` parses, PNG IHDR dimensions are 180/192/512/512, `tsc --noEmit` clean. **Not yet browser-verified** — Chrome installability and the actual `beforeinstallprompt` fire must be confirmed after deploy (D-15 depends on this).

### C-10 · Trading simulator hands out repeatable free money at 07:00 WIB
`src/app/(app)/tools/trading/page.tsx:116-176` (esp. `:117-118`, `:125`)

`calculatePriceHistory` derives `dayIndex = Math.floor(startOfDayTick / 43200)` and seeds each day with `let price = 50 + seededRandom(dayIndex) * 150`, rebuilding the whole chain every tick anchored on **UTC** midnight (`setUTCHours(0,0,0,0)`). An open position (`finy_trading_pos` in localStorage) survives the boundary but its `averagePrice` is compared against a completely unrelated base.

Simulated for 2026-09-19 UTC:

| UTC hour | WIB hour | price |
|---|---|---|
| 00 | 07 | 78.69 |
| 02 | 09 | 3,287.65 |
| 04 | 11 | 309,546.21 |
| 06 | 13 | 22.84 |
| 12 | 19 | 34.70 |
| 23.98 | 06.98 | 89,955.25 |

**Symptom:** buy near the end of the UTC day when the walk has crashed to ~22, hold across 07:00 WIB, and the next day's base is a fresh uniform draw in [50, 200] → **~4-9x risk-free profit, repeatable every morning.** The mirror case is -99.99% overnight. The reset lands at exactly the hour the target audience wakes up and opens the app. Intra-day swings of four orders of magnitude also make the chart nonsensical.

**Fix:** seed from the tick alone, carrying the previous day's close forward as the next day's open; add a mean-reverting drift term and clamp per-tick moves instead of compounding ±35% every 2 seconds.

### C-13 · The error-detection guard can never fire, so C-12 always runs
`src/app/(app)/ai-assistant/page.tsx:189-194` (throw at `:144-145`)

Verified against the installed `@supabase/functions-js@2.110.1`: on any non-2xx, `invoke` returns `{ data: null, error: FunctionsHttpError }` whose `.message` is the generic `'Edge Function returned a non-2xx status code'`. The server's `{ error: 'AI_SERVICE_ERROR' | 'AI_NOT_CONFIGURED' }` body is reachable only via `error.context` (the raw `Response`) — never via `data`. So every `errMsg.includes(...)` check is false → `isKnownError === false` → fake-reply branch. Separately `errMsg.includes('credits')` is lowercase while the token is `'INSUFFICIENT_CREDITS'`.

**Symptom:** a missing `GEMINI_API_KEY`, a 429, and a 500 all look identical to a successful AI answer. **Commit `cf9e487` ("bubble up Gemini API/credits configuration errors") does not work**, and you cannot debug AI failures from the client at all.

**Fix:** `const body = await (error as any).context?.json?.().catch(() => null)` and branch on `body?.error`; make comparisons case-insensitive.

**Status — fixed in working tree (2026-09-19), `npx tsc --noEmit` clean.** The catch block now reads `err?.context?.json?.()` for the real body, derives `code` from `body?.error ?? err?.message`, uppercases it, and branches on `INSUFFICIENT_CREDITS` / `UNAUTHORIZED` / `RATE_LIMIT|TERLALU BANYAK` etc.; `INSUFFICIENT_CREDITS` is delivered HTTP 200 by `monthly-conclusion`-style paths so the success branch also got `if (data?.error) throw new Error(data.error)`. The three fabricated-financial-data fallbacks (C-12's chat mock) are gone from this path — a failure now shows a real error string, never made-up Rp figures. **Residual (server-side, not this finding):** `ai-assistant/index.ts:250-258` masks `AI_NOT_CONFIGURED`/`AI_SERVICE_ERROR` into a generic Indonesian string before returning, so those two client branches can't currently match; the user still sees a genuine error (not fake data), but distinguishing "key missing" needs the function to pass a machine-readable code. Flagged as a follow-up; not changed here to keep this deployment client-only.

### C-14 · RLS does not validate that referenced `wallet_id` / `category_id` belong to the caller
`db_dump.sql` — insert policies on `transactions`, `budgets`, `recurring_rules`

FKs check existence only. A user can insert a row pointing at an arbitrary UUID in `wallets`/`categories`.

### C-16 · All VIP gating is client-side and trusts a localStorage cache
`src/store/auth.ts:31-38,138-140` · `src/hooks/useFeatureAccess.ts:8` · `supabase/functions/ai-assistant/index.ts:57`

`auth.ts:31-38` hydrates `user` synchronously from `localStorage['finy_user_profile']` before any server call, and `:138-140` writes the full profile — including `is_vip`, `ai_credits`, `vip_until` — back to that key. Every gate is a pure client render. Migration 009's hardening correctly blocks a *direct* `is_vip` write but does nothing about the client believing a tampered cache.

The AI tier is a second localStorage counter (`finy_ai_usage_date` / `finy_ai_usage_count`), and `ai-assistant/index.ts:57` states outright `// H-1: Daily limit checks are enforced on the client side`. That function calls only `check_rate_limit(30, 5min)` — never `consume_ai_credit`, never an `is_vip` check — unlike `parse-receipt:47`, `chat-financial:44`, `monthly-conclusion:42`.

**Symptom:** `localStorage.setItem('finy_user_profile', JSON.stringify({is_vip:true, ai_credits:9999}))` + reload unlocks Insights, custom categories, receipt upload, and the "VIP 50x/day" tier for free. Clearing two more keys resets the AI counter indefinitely. **`check_rate_limit(30,5)` permits ≈8,640 Gemini calls/day/user on your key.** Direct revenue loss and unbounded cost, with no server-side signal.

**Fix:** make `ai-assistant/index.ts` read `is_vip`/`vip_until` server-side and enforce the daily tier there (a `check_ai_daily_quota()` RPC mirroring `consume_ai_credit`). Treat the localStorage profile as a render hint only.

### C-17 · No middleware; auth is client-only and stale cache is trusted as authentication
no `middleware.ts` / `src/middleware.ts` exists (verified) · `src/components/layout/AppShell.tsx:51-97` · `src/store/auth.ts:29-52` · `src/store/transactions.ts:88-101`

Three related defects:
1. All 23 routes prerender as `○ (Static)` — nothing runs server-side. `AppShell`'s guard is a `useEffect` calling `router.replace('/sign-in')`, but the render path below it has **no `if (!user) return null`**, so lines 84-97 render the full chrome (Sidebar, BottomNav, modal, `{children}`) to an unauthenticated visitor for at least one paint.
2. `initialize()` synchronously does `set({ user: JSON.parse(localStorage['finy_user_profile']) })` before validating a session. If `getSession()` loses the 2-second `Promise.race` at `:45-49`, control jumps to `catch`→`finally`, so **`onAuthStateChange` at `:52` is never registered** and `session` stays null — but `user` is still the cached profile, and no `SIGNED_OUT` event will ever arrive to clear it.
3. `fetchTransactions` catches *any* error — including 401/403 — and serves `localStorage` with no stale flag.

**Symptom:** visiting `/home` logged-out flashes the app shell before bouncing. **Fix:** add `src/middleware.ts` using `@supabase/server`'s `createServerClient` to refresh the session and redirect unauthenticated requests away from `/(app)/*`. In `AppShell`, add `if (!user) return <spinner/>` before the app-container return. ## Part 3 — High severity

### Payments

**H-01 · Sandbox/production switches are independent → guaranteed go-live failure.**
`layout.tsx:37-49` picks `snap.js` from `NEXT_PUBLIC_MIDTRANS_SNAP_URL` in **Vercel** env; `create-subscription:82-88` and `verify-payment:68-74` pick the API endpoint from `MIDTRANS_IS_PRODUCTION` in **Supabase** secrets. Nothing ties them together. Flip one and not the other → backend mints a *production* token, browser loads *sandbox* `snap.js` with a sandbox client key, `window.snap.pay(prodToken)` fails. Also, if `NEXT_PUBLIC_MIDTRANS_CLIENT_KEY` is unset, `data-client-key` is omitted and snap.js refuses to initialise.
**Symptom:** 100% of production payments fail at checkout with a generic "payment declined" — and it's hard to diagnose because sandbox works perfectly.
**Fix:** derive both from one `NEXT_PUBLIC_MIDTRANS_IS_PRODUCTION` flag; throw at build time if the client key is missing or its prefix (`SB-Mid-client-` vs `Mid-client-`) disagrees with the flag.

**H-02 · No `callbacks.finish` → the redirect fallback never returns and never verifies.**
`create-subscription:96-118` has no `callbacks` block, so Midtrans shows its own default page. Meanwhile `upgrade/page.tsx:70-78` — taken whenever `window.snap` is undefined — does `window.location.href = redirectUrl` and **never calls `verifyPayment`**. `window.snap` is routinely undefined: `layout.tsx:48` uses `strategy="afterInteractive"`, ad-blockers strip payment scripts, and in-app WebViews / PWA standalone are unreliable.
**Symptom:** those users pay and land on a Midtrans page with no route back. VIP then depends entirely on the webhook — and nothing in `README.md` or `vercel.json` documents registering that URL.
**Fix:** add `callbacks: { finish, error, pending }` pointing at `${APP_URL}/upgrade?order_id=…&status=…`, and on mount read `order_id` from `useSearchParams()` and call `verifyPayment` + `checkVipStatus`.

**H-03 · `verify-payment` and `midtrans-webhook` race → double referral credits, silently skipped voucher.**
Both are read-then-write with no transaction, no row lock, no conditional update. The upgrade page deliberately calls `verifyPayment` from Snap's `onSuccess` at exactly the moment Midtrans POSTs settlement; both read `status='pending'` and both proceed. The referral guard is check-then-act: `.select(...).eq('rewarded', false)` then a **separate** `.update({rewarded:true})` that does not re-assert `rewarded = false`. Both call `increment_ai_credits(referrer, 5)` → **+10 instead of +5**. Knock-on: the `count % 3 === 0` voucher check re-counts *after* the fact, so under concurrency `count` can step 2 → 4 → 5 and never land on a multiple of 3 → **the VIP voucher is never granted.**
**Fix:** make the claim atomic and let its result drive everything —
```ts
const { count } = await adminClient.from('referral_uses')
  .update({ rewarded: true }).eq('id', referralUse.id).eq('rewarded', false)
  .select('id', { count: 'exact', head: true });
if (count !== 1) return;
```
Better: extract both duplicated blocks into one `security definer` RPC `grant_referral_reward(p_referred_user_id uuid)`. Gate VIP activation on `update subscriptions set status='active' … where order_id=$1 and status='pending'` returning exactly 1 row.

**H-04 · `midtrans-webhook` returns HTTP 200 on every uncaught error.**
`:214-221`, comment *"Return 200 to prevent infinite provider retry"*. Midtrans retries **only** on non-2xx, so a transient Supabase 5xx, pooler timeout, or cold-start failure permanently loses a paid settlement — the row stays `pending` forever with no reconciliation job.
**Fix:** return `500` from the catch so Midtrans retries with backoff; keep `200` only for signature-valid-but-unknown-order and already-processed. Add a scheduled sweep re-querying `/v2/{order_id}/status` for rows still `pending` after N minutes.

**H-05 · `has_vip_voucher` is a boolean, so earned vouchers are destroyed instead of stacking.**
`verify-payment:156-161`, `midtrans-webhook:172-177`. A referrer who earns 6 rewarded referrals before redeeming gets the flag set twice — one flag, one redemption. The second free month is silently destroyed, with no record and no way to detect it afterwards. Affects exactly the top referrers the program exists to reward.
**Fix:** `vip_vouchers integer not null default 0`, `+1` on grant, redemption guarded by `where vip_vouchers > 0` plus a decrement, all inside the existing `security definer` function.

**H-06 · `upgrade/page.tsx` always declares success, ignoring the verification result.**
`:41-52` awaits `verifyPayment` and `checkVipStatus` but **discards both**, then unconditionally toasts "Selamat! Finy Pro aktif" and routes home. `verifyPayment` swallows every failure into `{success:false}` and never throws (`purchases.ts:78-81`).
**Symptom:** a 404 (the C-08 case), a 429, a timeout, or a still-`pending` transaction all produce the identical success toast over a home screen still showing the Free badge. The user concludes they were scammed; support gets no signal.
**Fix:** branch on `res.success`, and **poll 3-4× with backoff** — Snap's `onSuccess` frequently fires before Midtrans marks `settlement`, so a single immediate call is *expected* to fail on a healthy payment.

### Core money

**H-07 · Editing any transaction from a past month is impossible.**
`transaction/new/page.tsx:13-19` does `router.replace('/home')` unconditionally. The modal survives (rendered globally at `AppShell.tsx:88`), but `/home` runs `fetchTransactions(currentMonth)`, so the store holds **this month only**. `NewTransactionModal.tsx:56-66` does `transactions.find(t => t.id === editTxId)` → `undefined` for any older transaction; since `editTxId` is truthy the reset branch doesn't run either, so the form keeps `amountStr='0'`. **H-09 · You can delete your only wallet, after which no transaction can ever be recorded.**

**H-11 · Logout clears almost nothing, and has no error handling.**
`auth.ts:104-110`: `await supabase.auth.signOut()` with **no try/catch**, then `set({user:null})` and removal of exactly **one** key (`finy_user_profile`).
Left behind: `finy_game_balance` and `finy_trading_pos` (**global**, not user-scoped), `@finy/pin` and `@finy/pin_enabled` (**global**), **`finy_ai_messages`** (**global**), `finy_ai_usage_date`/`finy_ai_usage_count` (**global**), plus the user-scoped `finy_txs_*`/`finy_wallets_*`/`finy_recurring_*`. In-memory Zustand stores (`transactions`, `wallets`, `categories`, budgets) are module singletons and are **never reset** — sign-out → sign-in-as-B is pure client navigation with no reload.
**Symptom:** on a shared/family device, user B sees A's game coins, is blocked by A's PIN, inherits A's AI quota, and — worst — **reads A's entire AI conversation about their finances.** There's also a window where A's transaction list renders under B's session. Separately, if `signOut()` rejects (offline, expired refresh token) the `set` and navigation never run: **the logout button silently does nothing**, with an unhandled rejection.
**Fix:** a single `clearAllLocalState()` wiping every `finy_*` and `@finy/*` key (keep `finy_locale`), called from a `finally` block, plus explicit `reset()` actions on every store. Scope the AI keys by userId going forward.

**H-12 · `verifyPin` fails open; PIN is plaintext; no brute-force protection.**
`security.ts:47-49`: `if (!pin) return true;` — delete just the `@finy/pin` key while leaving `pin_enabled === 'true'` and **any six digits unlock**. PIN stored cleartext at `:38-41`. `AppLock.handleKeyPress` has no attempt counter, delay, or lockout against a 10⁶ keyspace. No biometric option despite being framed as a security control.
**Fix:** store only a salted PBKDF2/SHA-256 hash; `if (!pin) return false` (fail closed); attempt counter in `sessionStorage` with exponential lockout. Be explicit in the UI that this is a screen-privacy lock, not real security — localStorage is readable by any XSS on the origin.

`transactions.ts:57-99`; no `AbortController`, no sequence token. Every caller re-fires on `month` change.
**Symptom:** tap "prev" twice quickly (Sep → Aug → Jul); if Aug resolves after Jul, the header says "Juli 2026" while the list, totals, pie chart and budget progress all show August. **The worst kind of bug in a finance app.**

**Symptom:** a month exceeding 1000 rows is silently cut off, and every total on Home/Stats/Budget/Export is computed over the truncated set. The export file is incomplete with no warning.

## Part 6 — Verified clean (do not re-investigate)

**Payments**
- **Midtrans SHA-512 signature verification is correct.** `midtrans-webhook:52-67` computes `SHA512(order_id + status_code + gross_amount + serverKey)` over the **raw string** `gross_amount` taken straight from the payload (`:31`) — which is what Midtrans actually signs (`"14999.00"`, not `"14999"`).
